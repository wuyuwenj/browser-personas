Design draft · v0 · for discussion

One Chrome, Many Agents

A CDP proxy that lets any number of coding agents share one Chrome and one profile, each owning its own tabs, each logged in as the persona it chose, with no tool able to see or touch another agent's work.

author James Wu, drafted with Claude date 2026-09-13 status pre-code, decisions open in §12
§1

Goal and non-goals

Goal. Run N agent sessions against one Chrome process with one on-disk profile. Each session owns 1 to 3 tabs. Sessions cannot list, attach to, navigate, or close each other's tabs. A session picks a named persona and gets that persona's cookies, and the persona's cookies survive Chrome restarts. Existing chrome-devtools-mcp users adopt it with one flag; users of other CDP clients adopt it with one address.

Why now. Today every session launches a full Chrome. On a 24 GB laptop that hit "out of application memory" at 11 sessions and 38 Chrome processes. The upstream fix, --browserUrl, shares the process but not the tabs, so the only isolation is a prompt rule ("act only on tabs you opened") that agents forget.

Non-goals

  • Replacing chrome-devtools-mcp, Playwright MCP, or agent-browser. The proxy sits under all of them.
  • A security boundary against a hostile local process. Isolation is between well-behaved agents, not against malware. §8 says exactly what is and is not protected.
  • Multi-machine or cloud browsers. Loopback only.
  • A GUI for editing personas. The CLI login flow and a YAML file cover it; the dashboard is read-mostly.
§2

Architecture

  agent A ─MCP─▶ chrome-devtools-mcp ─CDP ws─┐
  agent B ─MCP─▶ chrome-devtools-mcp ─CDP ws─┤    :9223                          pipe fd 3/4
  agent C ─MCP─▶ Playwright MCP ──────CDP ws─┼─▶ tab-scope proxy ───────────▶ Chrome, one profile
  script  ─────▶ puppeteer.connect() ─CDP ws─┘    │  ownership · persona · env      (no --remote-debugging-port)
                                                  │
  agent A ─MCP─▶ persona-registry MCP ──reads──▶ ~/.config/tabscope/personas/*/
  human   ─────▶ dashboard http://127.0.0.1:9223/   (live owners, tabs, personas)

Three pieces, one shared state directory. The proxy is the product. The registry MCP and the dashboard are thin views over the same files and the proxy's runtime state.

Key choice

Chrome is launched with --remote-debugging-pipe, not a port. Only the proxy holds the pipe, so there is no back door around the scoping. Every client, including the dashboard, goes through :9223.

Upstream connections are 1:1. Each client WebSocket gets its own CDP session multiplexed over the pipe by the proxy, and Chrome sees each as a distinct client with its own sessionId space. The proxy filters per connection rather than demultiplexing one shared upstream. This is more file descriptors and far less protocol surgery.

§3

Components

Daemon

Launches and supervises Chrome, owns the pipe, serves :9223. Auto-starts on the first client connection behind an atomic mkdir lock; explicit stop. Restarts Chrome on crash and replays persona cookies into fresh contexts. Headless by default; §12 D2.

Proxy

HTTP endpoints that mimic Chrome (/json/version, /json/list, /json/new, /json/close, /json/protocol) and the WebSocket paths /devtools/browser/<id> and /devtools/page/<id>. Persona is chosen by path prefix: /p/katy/json/version. Bare / is the shared default persona.

Ownership engine

Maps every target and every CDP session to an owner. Filters events and results, refuses cross-owner commands, applies tab caps and idle reaping. §5 has the full table.

Persona store and cookie vault

One directory per persona: manifest, notes, encrypted jar. The proxy restores a jar into a browser context when that context is created and saves it back on close. §4.

Registry MCP

Five tools so an agent can choose and annotate a persona: list_personas, verify_persona, note_persona, add_persona, remove_persona. Plus one prompt, /personas, that renders the list. Returns derived facts only, never cookie values.

CLI

init, login, list, edit, rm, status, stop, init --revert. §9.

Dashboard

One page served by the proxy. Chrome state and RSS, personas with login state, owners with their tabs and URLs, and three buttons: close tab, evict owner, re-login persona. A "watch" link per tab opens Chrome's DevTools frontend against that target so a human can look without stealing it.

§6

Lifecycles

Client connects

  1. GET /p/katy/json/version returns a webSocketDebuggerUrl that embeds the persona and a fresh or supplied owner id.
  2. On WebSocket open the proxy opens its own upstream session over the pipe, creates or reuses the katy browser context, and restores the jar if the context is new.
  3. If the owner id matches one inside its grace window, its targets are reattached and the grace timer cancels.

Tab creation and the attribution race

Chrome emits targetCreated to every client before the createTarget response reaches the caller. So at the moment the event arrives, nobody owns the target. The proxy holds unclaimed targetCreated events in the pending queue; when a createTarget response with that targetId arrives on owner X's connection, X takes the target and only X's queued copy is released. Events that are never claimed within 2 s belong to a human and stay hidden. Popups arrive with openerId and inherit immediately, no queue.

Disconnect

Tabs enter a grace window (default 120 s) so a Claude Code /mcp reconnect gets them back. After that, close them and save the persona jar if dirty. Grace is the one knob exposed in config.

Idle reaping

A target with no CDP traffic for 15 minutes is closed and its owner told on next command. Owners with zero targets and no traffic for 30 minutes are evicted. Both thresholds configurable.

Chrome crash

The daemon relaunches Chrome, recreates every persona context, restores jars, and returns Target.targetCrashed to each owner for its old targets. Clients reconnect on their own; chrome-devtools-mcp already handles a dropped browser.

Persona delete

Refused while any owner holds it, naming the owner. Otherwise: close tabs, dispose the context, shred the jar, remove the directory.

§7

Persona selection and identity

Two ways to choose a persona, both landing on the same context:

  • By URL path. --browserUrl=http://127.0.0.1:9223/p/katy. Works for every CDP client, no tool call needed. This is the default the CLI writes.
  • By context name. new_page(url, isolatedContext: "katy") from chrome-devtools-mcp. The proxy maps the name to the persona. This lets one MCP session hold tabs in several personas.

A persona marked exclusive is leased to one owner at a time; a second requester gets a refusal that names the holder. This is the current profile-lease behaviour, moved to where the conflict actually is.

Co-tenancy: sharing is the default, and the agent is told

A persona without exclusive accepts any number of owners. Each gets its own tabs in the same context and the same login. Because CDP has no channel for a note, the notice reaches the agent through the tool layer:

  • list_personas returns holders: [{ owner, tabs, since }] and a one-line sharing sentence per persona.
  • An exclusive refusal names the holder: "katy is held by owner ttys004 since 14:02 with 2 tabs. Pick another persona or wait."
  • The wrapper packaging (moved from v0.4 to v0.3) appends one line to the first new_page result on a shared persona: "Shared login: 1 other agent holds katy. Your tabs are yours; your actions are attributed to the same user." This is the only path that reaches an agent that never asked.
  • init --hooks optionally installs a Claude Code PreToolUse hook that announces the same before the first browser call.

The notice always states what sharing means: one server-side session, so a write by either agent is attributed to the same user, and a logout by one logs out both.

Owner identity. The proxy needs a stable owner id to reclaim tabs after a reconnect. The launcher wrapper derives one from the parent process's controlling tty and passes it as ?owner=; scripts pass their own. With no id given, ownership is the connection and reclaim is off.

Subagents. Claude Code subagents share their parent's MCP connection, so parent plus subagents are one owner. The upstream pageId routing separates them inside that owner. Nothing extra needed.

Decision D3

Shared login only, or persona contexts from day one? Persona contexts are the general case and the shared login is the degenerate case where every owner maps to the default context. Recommend building contexts first so the shared case costs nothing extra.

§8

Security model

Protected

  • A well-behaved agent cannot see, attach to, navigate, or close another owner's tabs, or read another persona's cookies through CDP. With --remote-debugging-pipe there is no port to bypass the proxy.
  • A staging persona cannot reach prod. The allowlist is derived from the manifest's account origins; Page.navigate and createTarget are refused off-list, and a proxy-installed Fetch interceptor blocks in-page navigations to foreign origins.
  • A read_only persona cannot submit. The same interceptor, installed at the request stage so it sees method, headers, and body, answers blocked requests with a 403 whose body names the policy, so the agent's network log explains itself. Read-only sessions also set Network.setBypassServiceWorker and refuse WebSocket upgrades off the allowlist, the two paths Fetch cannot see. This is the standing "prod browser is read-only" rule, enforced by the tool.
  • Jars are AES-256-GCM with a key held in the macOS Keychain, matching Chrome's own cookie encryption. On Linux, age with a 0600 identity file. Plaintext jars are never written.

Read-only has three levels

"GET only" is the wrong rule for apps that read through POST. Every Next.js server action is a POST with a Next-Action header, and GraphQL reads are POSTs too, so a strict persona would load a page shell and nothing inside it.

LevelAllowsFits
strictGET, HEAD, OPTIONSREST sites, marketing pages, RentVine's UI
inspectplus POST whose body matches a rule, e.g. GraphQL query but not mutationGraphQL apps
cooperativeplus POST carrying X-Read-Only: 1, which the proxy stamps on every request and the app honoursNext.js server actions, opaque on the wire

Cooperative mode is the honest one for server-action apps: the proxy cannot tell a read action from a write action, so the app decides. In next-app that is one check in loadAdminContext plus an annotation of which actions write, which the existing authz scanner already walks.

Not protected

  • A malicious local process. It can read the config directory as your user. Same as Chrome itself.
  • Two owners on the same non-exclusive persona share one server-side session. Logout in one logs out both. The proxy denies navigation to configured logout paths, which covers the common accident, not intent.
  • Notes are text written by other agents. The registry returns them as data with author and age; never as instructions.

Install and CLI

npx tabscope init                 # detect Chrome; write or rewrite MCP entries for Claude Code, Codex, Cursor
npx tabscope login katy --env staging --origin https://stage.doorvest.com
                                  # opens a throwaway headed Chrome, "log in, then press Enter",
                                  # exports + encrypts the jar, writes the manifest, asks for a description
npx tabscope list                 # personas, login state (last probe), holder, tab count
npx tabscope edit katy            # $EDITOR on manifest.yaml; hot-reloaded
npx tabscope rm katy              # refused while held
npx tabscope status               # daemon, Chrome pid + RSS, owners → tabs → URLs
npx tabscope stop
npx tabscope init --revert        # restore the original MCP configs

What init writes. For an existing chrome-devtools entry it adds --browserUrl=http://127.0.0.1:9223 and keeps every other flag. For an existing playwright entry it adds --cdp-endpoint. For a fresh install it writes a launcher as the MCP command that execs npx chrome-devtools-mcp@latest --browserUrl=… "$@", so a user who pastes the upstream README config verbatim still lands on the proxy. It also writes the personas registry entry beside it.

Login uses a throwaway Chrome. The daemon may be headless, and Chrome cannot switch modes live, so login spawns a separate headed Chrome on a temp profile, lets the human clear the captcha, exports cookies over CDP, and imports them into the daemon's context. The jar is the artifact; the temp profile is deleted.

Config locations. ~/.config/tabscope/config.yaml for daemon settings (port, grace, idle, headless, Chrome path). ~/.config/tabscope/personas/<name>/ for personas. An optional repo-local .tabscope/personas/*.yaml holds committed manifests for a team; jars stay per machine.

§12

Open decisions

D1

Owner identity source

Connection-only (simple, no reclaim) versus ?owner= derived from the parent tty by the launcher (reclaim works, one more moving part). Recommend the tty-derived id with connection-only as the fallback.

D2

Headless or headed daemon

Headless is quieter and removes foreground stealing. Headed lets a human glance at a window. The dashboard's watch link covers glancing. Recommend headless default, headless: false in config.

D3

Personas in v0.1 or v0.2

Contexts are the general case. Shipping shared-login first gets the demo out sooner. Recommend v0.2 as scheduled; the demo does not need personas.

D4

Agent-created personas

May an agent run the login flow and save a new jar, or is the registry human-curated? Self-healing versus junk accumulation. Recommend human-curated in v0.3; revisit with usage.

D5

Language

Node/TypeScript matches puppeteer, chrome-devtools-mcp, and the npx install story. Go or Rust would give a single binary and a lower idle footprint. Recommend TypeScript; the proxy is protocol plumbing, not compute.

D6

Name

tabscope is used above as a placeholder. Check npm and GitHub before committing.

§13

Risks

  • Handshake drift. A puppeteer-core major can change the connect sequence and break attribution silently. Mitigation: the CI matrix in §10 and an integration test that fails loudly when a client sees a foreign target.
  • Upstream absorption. chrome-devtools-mcp could add client-scoped target visibility. The persona vault, env enforcement, and multi-client generality would survive that; ownership alone would not.
  • OpenChrome. Already ships a broker with tab routing for its own toolset. The proxy's answer is that it works under chrome-devtools-mcp and Playwright, which OpenChrome replaces rather than supports.
  • Fetch interception cost. Installing Fetch.enable on every session adds a round trip per request. Only install it for personas with an allowlist or read_only; the shared default persona pays nothing.
  • Cookie-only persistence. Apps that keep auth in localStorage lose it across restarts. Doorvest's Cognito tokens are cookies. Add DOMStorage save and restore per known origin in v0.4 if a user needs it.
Built

v0.1 — what the code taught us

Shipped 2026-09-14. 31 unit tests, 11 integration tests against a real Chrome 152, all green. The exit criterion holds: two real chrome-devtools-mcp servers on one Chrome, and each list_pages shows only its own page.

Four defects the tests caught, none of which the design predicted

  • A tab is two targets. Chrome 152 answers Target.createTarget with the PAGE id, but first announces a separate tab target that wraps it — a different id, with no field linking the two. Claiming only the returned id left the tab unowned, its attach events held then dropped, and every client hung for 30 s on newPage(). Fix: one create is in flight at a time across all owners, so the window a tab appears in unambiguously names its creator.
  • A refusal with no session id reads as a hang. Puppeteer routes responses by sessionId before it looks at the request id, so a refusal answered at browser level landed in the wrong callback map and the caller's promise never settled. The agent sees a 60 s timeout instead of "no". Every local reply now echoes the command's session.
  • Sessions bound at delivery are bound to nobody. Chrome attaches to a new tab before the response claims it, so binding a session to an owner at attach time bound it to nothing and every later frame on it was dropped. Session access is now derived from target ownership, which resolves correctly once the claim lands.
  • Chrome's own furniture was being held. The omnibox popup, extension background pages and service workers all auto-attach, and a client asking for waitForDebuggerOnStart leaves each paused. Holding them stalled renderers for the whole claim window. Only page and tab are ownable at browser level; everything else is dropped on sight and unblocked.

Deviations from this spec, and why

  • §2 said 1:1 upstream connections; the build multiplexes. A pipe is a single connection by construction, so the proxy rewrites ids and routes responses per client. The pipe's security property is what mattered, and it is kept.
  • §5's auto-detach of foreign targets does not apply. With one upstream connection there is one attach per target, so detaching would take the owner's session with it. Non-owners simply never receive the event.
  • The path form (/p/<persona>, /o/<owner>) cannot work with --browserUrl. Puppeteer resolves /json/version as an absolute path, discarding any path or query on the base URL. Naming an agent therefore requires the --wsEndpoint form; --browserUrl still isolates, with a per-connection identity and no reclaim. The launcher that derives an owner from the tty (D1) moves to v0.2.
  • The tab cap counts pages, not targets. Tab wrappers, iframes and workers are owned so their events route, but they were never what the limit meant.

A test that proved nothing

Disabling filterTargetInfos entirely left the MCP isolation test green. list_pages reads puppeteer's own registry, built from events, not from Target.getTargets — so the filter is real but only for clients that call that method directly. The guarantee for every puppeteer-based client lives in event routing, and mutating that fails the test. Worth stating plainly: without the mutation pass, v0.1 would have shipped with a headline test that could not fail.

v0.2 — personas

Shipped 2026-09-14. 43 unit tests, 18 integration tests, all green. Exit criterion met against the real application: two agents in one Chrome signed in as two different users at the same time, both still signed in after the daemon and the browser restarted, and a staging persona that cannot be navigated to production.

Three defects the real app caught

  • An origin allowlist on subresources breaks every application. Scoping the persona to its own app's origin blocked the app's own auth provider, and the login simply failed with a 400 from the identity service. The rule worth having is "this agent cannot NAVIGATE to production", so the allowlist now applies to top-level document loads only. read_only still applies to every request, because a write is a write wherever it goes.
  • Interception armed at the routing decision never armed at all. A page's attach event usually arrives while its tab is still unclaimed, so it is held and then released straight to its owner — a path that bypasses the decision entirely. Arming moved into delivery, the one point every path to an owner passes through.
  • Puppeteer turns the policy off during its own setup. It calls Fetch.disable on every new page session, which silently switched read-only off. That call is now answered locally as a success and never forwarded; the proxy owns Fetch on a restricted session.

Deviations

  • Jars are saved unconditionally, not on a dirty flag. Detecting "cookies changed" needs the Network domain enabled, which depends on what the client happened to ask for. A missed save means a persona silently logged out on the next restart, and one Storage.getCookies per persona is cheap.
  • Two test-harness bugs worth naming, because both look like product failures: a form whose submit button stays disabled until React sees real key events (setting value is not enough), and an in-page waitForFunction that dies with "execution context was destroyed" at the exact moment the navigation it waits for succeeds. Poll from outside the page.

v0.3 — the registry, and knowing you are not alone

Shipped 2026-09-14. 43 unit tests and 25 integration tests. The wrapper re-exports chrome-devtools-mcp's whole toolset beside five persona tools, so an agent reads list_personas and picks its own identity; the dashboard gives a human the same picture with a watch link per tab.

What changed from the plan

  • The co-tenancy notice rides on the first new_page, and only then. CDP carries no channel for a note to a model, so the tool layer is the only place it can land. Repeating it on every call would make it furniture; three mutations pin that it appears, appears once, and does not count the agent itself as a co-tenant.
  • Wrapper packaging moved from v0.4 into v0.3, because without it there is no path for the notice to reach an agent that never asked.
  • The MCP SDK needs zod v4. Installing the SDK alone resolves zod 3 and the server dies at import with a subpath-export error that names neither package usefully.

A test that reports the machine, not the code

The two sign-in end-to-end tests now skip when swap is more than 90% full. They passed repeatedly, then began failing on a host with 0.2 GB free and 27.2 of 27.6 GB of swap in use — a real browser driving a real auth round trip on a fixed time budget cannot be reliable there, and a red test meaning "your laptop is full" is worse than one that says so. The irony is the point: this is the resource exhaustion the project exists to reduce, observed while building it.

Still open

  • Signing two personas in back to back inside one process is unreliable against this application's auth client. The isolation is proven — separate contexts, separate cookie stores, a full AuthenticationResult for each — but the e2e signs each persona in on its own connection and asserts both at once after a restart, which is the stronger claim anyway.
  • Per-owner audit logs and rate limits, localStorage persistence for apps that keep auth there, and Linux vault coverage.

v0.4 — the console

Shipped 2026-09-14. 53 unit tests and 33 integration tests. §9 said not to build a web form for personas, and that was wrong about the half that mattered: editing a manifest is five fields in a file, but the login flow needed a terminal, a second browser, and a keypress at the right moment, with no signal when the target was not even running.

What the page owns

  • Login by polling, not by a keypress. The old flow asked the human to press Enter when done, which is a claim the tool cannot check. The session now asks the application, through the cookies the login is producing, so the green dot is the app's answer rather than the user's.
  • Passwords, opt-in. A jar holds a session that expires; a password does not. Stored with the same key, never rendered back, never returned by an endpoint, never in a tool result — and off unless asked for.
  • Create, edit, delete, with delete refused while an agent holds the persona.

Three guards a write surface needs that a read surface does not

A token minted per daemon and carried in the link; a loopback Host, which is what DNS rebinding controls and a browser cannot forge; and JSON on any write with a body, which a cross-site form cannot send. The CDP endpoints stay ungated — chrome-devtools-mcp has nowhere to put a token, and they expose no credentials. All five guards are mutation-verified.

A custom launcher is not wrappable

Dry-running init against a real config found an entry running a lease script that picks a Chrome profile at runtime. The shim strips only the browser-choosing flags it can see in the config, so wrapping that would produce a server that adds --userDataDir next to our --wsEndpoint and dies on start. Those entries are now detected, left alone and reported, with --replace-launcher to swap in the bundled upstream — which is the honest resolution, since picking a browser is the job this tool takes over.

Three defects the tests caught

  • A bodyless DELETE cannot carry a content type, so requiring JSON on every write made the console's own delete button unusable. The rule now applies only when a body is present; a bodyless cross-site write is still stopped by the Origin check and by a preflight no form can avoid.
  • An edited manifest never reached the copy the daemon serves from, so a change took effect only after a restart.
  • Gating /status broke the registry MCP, which reads it. It runs as the same user, so it reads the token file rather than being handed one.
  • Node's fetch silently drops a Host override, so the rebinding test passed for the wrong reason until it was rewritten as a raw request. A guard test that cannot send the attack is not a test.

v0.5 — any site, any login method

Shipped 2026-09-14. 59 unit tests and 36 integration tests. The persona model assumed a username, a password and one origin. Every one of those assumptions breaks on a Google or SSO login, and the first was a real defect rather than a gap: a persona fenced to its own app could never complete an OAuth sign-in, because the redirect to the provider was off its own allowlist.

What a login now captures

  • Web storage, not just cookies. Firebase, Supabase, Auth0's SPA SDK and MSAL keep their tokens in localStorage. A cookies-only jar restores a session the application still treats as signed out, which looks exactly like a broken tool. Reading and writing it needs a document on that origin, so both directions open a throwaway tab.
  • Cookies for every origin the login touched, which was already true and turns out to be the thing that makes a later silent re-auth work.
  • The provider's origins, recorded as auth_origins and allowed. They are learned from a real sign-in rather than configured, so allowing them grants nothing the app does not already do.
  • The signed-in path, inferred from wherever the login landed, when none was given.

The jar gained a version. A v1 jar is a bare cookie array and is still read, because upgrading should not log every persona out.

The defect the test caught

The upstream adapter dropped sessionId, so every Runtime.evaluate meant for a page ran at browser level instead — succeeding, and doing nothing. Storage capture and replay both silently no-opped. Worth stating as a rule: a CDP call that must run inside a page is meaningless without its session, and the failure is silent in both directions.

v0.6 — a persona is a person, not an account

Shipped 2026-09-16. 59 unit tests and 43 integration tests. The manifest always held an array of accounts; the console and the API only ever touched the first one, which made the array a lie.

The bug behind the missing feature

Signing in to a second website would have logged the persona out of the first: the login ran in a throwaway browser and replaced the jar wholesale. It now starts from the persona's existing session — cookies and web storage both — so the capture at the end is a union, and the human arrives already signed in to everything else, which is what they expect anyway.

Websites are keyed by origin, never by index

A positional API lands the edit on the wrong site the moment a row is removed between read and write, and does it silently. Removing the last website is refused outright: an empty allowlist means "unscoped", which is the opposite of what removing the last site should mean, so deleting the persona is the honest way to do it.

A test that proved nothing, again

The first version of "keeps the first website's session" wrote a jar by hand and asserted it read back — which passes whether or not the merge exists, and the mutation run said so. Replacing it needed a seam: a fake CDP client, so the session's decisions can be asserted without a browser window opening. Second time a headline test has survived deleting the thing it names; the mutation pass is the only reason either was caught.

The console pauses its own live refresh while a form is open. A two-second re-render of a settings page wipes whatever is half-typed, and that is a self-inflicted wound worth naming.

v0.7 — the console stops asking twice

Shipped 2026-09-16. 68 unit tests and 50 integration tests. After a sign-in, the username fills itself in.

Two sources cover nearly every login shape. The first is the address the human typed, watched across the whole journey rather than on the app's own page — which is the detail that makes it work for SSO, since Google and Okta host that field themselves. The second is the ID token the sign-in left in the session: an OAuth login shows the app no password and no form, but the token it leaves names the user. Its signature is not checked and does not need to be; nothing is being authorised, a label is being read off a token already in our own vault.

A hole the test found immediately

A JWT is dot-separated word characters, so it sailed through a naive username pattern and would have been written into the manifest as somebody's name. Length alone does not separate the two — the shape does: three or more segments with a long one. A name with dots in it is still a name.

A username set by hand is never overwritten, and a value with whitespace is refused outright, so a mis-guessed selector cannot put a password in the manifest.

v0.8 — the login saves itself

Shipped 2026-09-16. 68 unit tests and 54 integration tests. Nobody should have to confirm something the application can answer.

The daemon now watches every sign-in in progress and saves it when the session becomes real. Two checks in a row have to agree. One is not enough: a multi-step sign-in passes through pages that are not the login page — a consent screen, an account chooser — and a probe can answer before a second factor is finished. A failed check resets the count, which is what makes a second factor landing late behave correctly rather than racing.

The watcher lives in the daemon rather than in the page, so a terminal login finishes by itself too, and closing the console tab mid-login does not strand a browser waiting for a click nobody will make. The keypress flow is gone entirely; both paths now share one implementation.

Two defects fixed alongside

  • finish was not idempotent. The watcher and the Save button can arrive together, and the second capture would run against a browser the first already closed — overwriting a good jar with whatever a dying session returns.
  • start refused a stale daemon too quietly. It printed to stderr, which went to a log nobody read, so an old daemon kept serving an old build while a restart looked like it had worked. Twice. It now says so on both streams and names the fix, and stop waits for the process to actually exit instead of returning while the port is still held.

A third test that proved nothing

"Captures once when the watcher and the Save button arrive together" asserted that both calls returned the same number — which they do whether or not the guard exists. Counting the captures is the assertion that matters. That is three headline tests in this project that survived deleting the thing they named, every one caught only by the mutation pass.

v0.9 — transparent mode

Shipped 2026-09-19. 82 unit tests and 58 integration tests. A user who already runs chrome-devtools-mcp keeps their entry, their flags and their 29 tools; init routes the entry through a shim, and from the agent's side nothing changed except that tabs are isolated and one Chrome is shared.

The wrapper is gone

v0.3 re-exported chrome-devtools-mcp's whole toolset to carry one sentence — the co-tenancy notice. That doubled the tool schema every agent loads on every session (~17k tokens) and tied this project to each upstream tool change. The notice now lives in list_personas; the registry is five tools and optional. The honest cost: an agent that never asks is not told. That is the right trade against a schema everyone pays for.

Why there has to be a shim

--browserUrl cannot carry a persona or an owner name, and a static config entry cannot hold a per-session id — every session using it would share one, and reclaim-after-reconnect would hand one session another's tabs. browser-personas exec computes the id at spawn time from the controlling terminal and runs the user's own command with the endpoint appended, stripping any browser-choosing flag they had, because a leftover --browserUrl would win the argument.

Upstream is bundled

chrome-devtools-mcp moved from a dev dependency to a real one. Resolution order is the user's own command, then the bundled copy, then npx @latest, and the shim says which on stderr. A version we tested beats a version we haven't; the CI matrix now tests exactly what ships. Chrome itself is never fetched quietly.

A custom launcher is not wrappable

Dry-running init against a real config found an entry running a lease script that picks a Chrome profile at runtime. The shim strips only the browser-choosing flags it can see in the config, so wrapping that would produce a server that adds --userDataDir next to our --wsEndpoint and dies on start. Those entries are now detected, left alone and reported, with --replace-launcher to swap in the bundled upstream — which is the honest resolution, since picking a browser is the job this tool takes over.

Three defects the tests caught

  • The owner id came out as tty--dev-ttys004: the prefix was added before /dev/ was stripped.
  • verify_persona reported "failed" for every persona. The daemon probed from about:blank, so the fetch to the app was cross-origin and CORS refused it. The tab now opens on the probe URL itself and asks same-origin.
  • list_personas told agents to use isolatedContext. chrome-devtools-mcp keeps that name internally and sends a bare createBrowserContext over CDP, so the proxy never sees it. The line was a lie; it now names the entry that actually works.

v0.9.2 — SSO, for real this time

Shipped 2026-09-23, from issue #1. Every login test until now used one origin, so nothing ever crossed to an identity provider. Four defects lived in that gap.

  • read_only: strict blocked every SSO sign-in. auth_origins fed the navigation fence but not the read-only check, and signing in is POSTs to the provider. Auth origins are now exempt from read_only; the promise is about the app.
  • Auto-save could capture a logged-out session mid-SSO. With no probe, "not the start URL and not a /login path" was the whole test, and an identity provider's page passes it. Now the page must be on the app's own origin, not look like a sign-in page, and the human must have typed or gone out and come back. The inferred probe is the app's path only — no query string, which held a one-time OAuth state.
  • A login never settled after the target swap. A cross-origin round trip can replace the page target; the session now follows the tab and re-attaches.
  • Hand edits to manifest.yaml were ignored until restart. The manifest is re-read when the file's mtime changes.

One mutation survived the first pass: every provider URL in the test contained signin, so the path guard masked the missing origin check. Google's /AccountChooser does not oblige; the test now includes it.
